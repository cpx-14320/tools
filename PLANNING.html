平台

平台架構

cpx-tools 是「一組共用帳號登入的小工具」：帳號系統（註冊／登入／session）整個平台只有一套，登入後在工具選單裡切換使用不同工具；每個工具自己的功能資料彼此獨立，只共用這一份帳號。

已確認：單一 Next.js 專案

整個平台是一個 Next.js 專案，裡面用路由切出每個工具（例如 /tools/expenses/...、/tools/transit/...），共用一份 User／session，不用處理跨專案登入。

待辦：目前 cpx-tools/expenses 是獨立 scaffold 出來的 Next.js 專案，要搬移／重新定位成平台本身（cpx-tools/ 專案根目錄），記帳本變成裡面 /tools/expenses 下的一個路由群組——實際動工時再處理這個搬遷。

工具 01

記帳本（Expenses）

多人共用的記帳本：計算每月薪水（多種明細可自訂）、記錄各類消費（分類可自訂）。以下規劃沿用既有的 MyMeal 技術棧——Next.js App Router、TypeScript、Tailwind、MongoDB + Mongoose、bcrypt + cookie session。

資料模型

Collection欄位說明
Useraccount, passwordHash, name, createdAt帳號制登入（平台共用一份，見上方平台架構）
Ledgername, ownerId, inviteCode, members: [{userId, role, joinedAt}]role 分 owner／member，owner 可移除成員、重新產生邀請碼
ExpenseCategoryledgerId, name, icon/color, createdBy帳本共用，任一成員新增其他成員都看得到
SalaryItemTypeledgerId, name, kind: "加項"|"扣項"帳本共用，例如本薪／獎金（加項）、請假扣款／勞健保（扣項）
SalaryRecordledgerId, userId, yearMonth, items: [{typeId, amount}], note淨額＝加項總和－扣項總和，即時計算，不另外存快取
TransactionledgerId, userId, categoryId, amount, date, note純支出紀錄；薪水以外的收入目前不在範圍內

頁面流程與功能邏輯

登入分流——新帳號註冊後、或登入後，選了記帳本這個工具，依照所屬帳本數量導向不同頁面：

/register /login

  • /register：填寫帳號、密碼、姓名 → 建立 User → 自動登入 → 依登入分流邏輯導向
  • /login：帳號密碼驗證（bcrypt 比對）→ 成功後依登入分流邏輯導向；失敗顯示對應錯誤訊息

/ledgers 建立／加入帳本

  • 建立帳本：輸入帳本名稱 → 建立 Ledger，自己是 owner，系統產生唯一邀請碼（比照 MyMeal memberCode 的「產生＋查重試」機制）→ 導向該帳本 /dashboard
  • 加入帳本：輸入邀請碼 → 查到對應 Ledger → 加入 members（role: member）→ 導向 /dashboard

/dashboard 當月總覽

  • 預設顯示當月，可切換月份
  • 計算邏輯（即時查詢彙總，不存快取數字）：
    1. 當月總收入＝該帳本當月所有成員 SalaryRecord 淨額加總
    2. 當月總支出＝該帳本當月所有 Transaction 金額加總
    3. 結餘＝總收入－總支出
    4. 分類佔比＝依 ExpenseCategory 分組加總 Transaction

/transactions 消費紀錄

  • 列表依帳本查詢，預設當月，可依分類／日期篩選
  • 新增：選分類（下拉，來自該帳本 ExpenseCategory）、金額、日期（預設今天）、備註（選填）→ 寫入 Transaction，記錄人＝目前登入者
  • 編輯／刪除：權限範圍待確認，見下方「待確認事項」

/categories 消費分類管理

  • 新增：輸入名稱（可選顏色／icon）→ 寫入 ExpenseCategory，帳本全員共用可見
  • 刪除：處理方式待確認，見下方「待確認事項」

/salary 薪資紀錄

  • 依月份列出帳本所有成員的薪資紀錄（全員可見）
  • 新增／編輯：選擇月份，依序輸入各薪資明細類型金額（類型已設定加項／扣項）→ 即時預覽加總淨額 → 儲存為 SalaryRecord
  • 一人一個月限一筆紀錄，重複新增視為編輯既有紀錄

/salary/types 薪資明細類型管理

  • 新增：輸入名稱＋選擇「加項」或「扣項」→ 寫入 SalaryItemType，帳本共用
  • 刪除：處理方式待確認，同分類刪除邏輯，見下方「待確認事項」

/members 成員管理

  • 列出帳本所有成員與角色
  • owner 可：重新產生邀請碼（讓舊碼失效）、移除成員（移除後該成員看不到此帳本，歷史紀錄保留並標示「已離開成員」）
  • member 僅能自己「離開帳本」，不能移除他人

/reports 報表

  • 月度／年度趨勢圖（收入、支出、結餘）、分類佔比圖
  • 屬開發第 5 階段，細節屆時再展開

工具 02

搭乘車查詢規劃完成・待開發

固定通勤路線（上下班搭特定班次的台鐵／公車／捷運／高鐵）的查詢與提醒工具：查時刻表，以及誤點或即將到站時主動推播通知。資料來源統一採用交通部 TDX 運輸資料流通服務，不用分別接各縣市或各業者自己的 API。開發順序排在記帳本之後，見下方「開發順序」。

外部資料來源：TDX 運輸資料流通服務

TDX（tdx.transportdata.tw）是交通部整合台鐵、高鐵、公車、捷運的官方開放資料平台，RESTful JSON、免費申請。所有端點都要加 /api/basic 前綴（例如 https://tdx.transportdata.tw/api/basic/v3/Rail/TRA/Station），下表已標示哪幾項是實際用真帳號打過、確認可用：

TDX 端點對照（路徑省略 /api/basic 前綴）
功能運輸工具Endpoint狀態
查時刻表台鐵/v3/Rail/TRA/DailyTrainTimetable/OD/{起站ID}/to/{迄站ID}/{日期}已串接 起訖站雙向都能查，車種不篩選、全部顯示；另外併查 StationLiveBoard 把誤點分鐘數疊上去
高鐵/v2/Rail/THSR/DailyTimetable/OD/{起站ID}/to/{迄站ID}/{日期}已串接 要給起訖站 ID，不是單站查詢
公車/v2/Bus/Route/City/{City}/{RouteName}已串接 用來取方向對應的終點站名稱
即時到站／誤點台鐵/v3/Rail/TRA/StationLiveBoard/Station/{StationID}已串接（與上面同一個 API）
公車/v2/Bus/EstimatedTimeOfArrival/City/{City}/{RouteName}已串接 用站名精確比對篩出單一站牌
捷運／輕軌/v2/Rail/Metro/LiveBoard/{RailSystem}待驗證 實測 TRTC 回傳的站點覆蓋很稀疏，目前仍用示範資料
已驗證的站碼

台鐵站名用傳統字「臺」、高鐵站名用「台」，兩套系統的 StationID 是分開的命名空間。已查到並寫進 lib/tdx-stations.ts：台鐵中壢 1100／臺北 1000／七堵 0930／基隆 0900；高鐵台北 1000／台中 1040／新竹 1030／左營 1070／板橋 1010；北捷（TRTC）古亭 O05。要加新站就用 /api/basic/v3/Rail/TRA/Station 這類站列表 API 查，不要憑記憶猜 ID。

認證與限制

OAuth2 Client Credentials：先在 TDX 會員中心（/user/dataservice/key）建立 API 金鑰取得 Client ID／Secret，再用 HTTP POST 向 https://tdx.transportdata.tw/auth/realms/TDXConnect/protocol/openid-connect/token（Header 帶 Content-Type: application/x-www-form-urlencoded，Body 帶 grant_type=client_credentials＋client_id／client_secret）換取 access token（效期 86400 秒／24 小時，已在 lib/tdx-client.ts 做記憶體快取＋自動重新換發）。免費「一般會員」額度查時刻表夠用，但即時到站是高頻輪詢，之後做背景推播時要注意不要對同一站打太密、只查使用者實際設定的少數路線。

已知限制

高鐵幾乎不提供可靠的即時誤點資料、且準點率極高，因此高鐵只做時刻表查詢，不納入誤點推播功能。捷運／輕軌的即時到離站實測覆蓋不穩定（TRTC 整個系統同時間只回傳數十筆、不保證每站都有），要再花時間確認資料規律才能接，目前維持示範資料。

資料模型

帳號沿用平台共用的 User（見上方平台架構），不另外做帳號系統。

Collection欄位說明
CommuteRouteuserId, label, mode: "TRA"|"THSR"|"Bus"|"Metro", originName, originStopId, destName, destStopId, routeKey, activeWeekdays, notifyBeforeMinutes, delayThresholdMinutes, enabled一條使用者設定的監控路線。routeKey 依 mode 意義不同：台鐵／高鐵存車次號或時間窗；公車存 city＋RouteName；捷運存 RailSystem＋線別。個人設定，不像記帳本的帳本資料需要共用
NotificationChanneluserId, provider: "telegram", chatId, enabled推播目的地；先只做一種管道（見下方「通知管道」待確認事項）

頁面與路由規劃

路徑功能

頁面流程與功能邏輯

/tools/transit/routes/new 新增監控路線

  • 選運輸工具（台鐵／高鐵／公車／捷運）→ 介面依 mode 切換選擇方式：台鐵／高鐵選車站＋車次（或不指定車次、改監控某時間窗內所有列車）；公車選縣市＋路線＋站牌；捷運選系統＋站
  • 設定提醒門檻：notifyBeforeMinutes（提前幾分鐘通知即將到站）、delayThresholdMinutes（僅台鐵／捷運適用，誤點超過多少分鐘才通知）
  • 設定 activeWeekdays（預設平日一～五，避免週末誤觸發上班提醒）
  • 儲存為 CommuteRoute，預設 enabled

背景輪詢與推播

Next.js 本身是 request-driven，沒有背景 worker，需要外部排程觸發一個輪詢用的 API endpoint（例如 Vercel Cron 或其他排程服務，定時打 /api/tools/transit/poll）：

  • 同一條路線在門檻內重複達標，應避免重複推播（例如同一班車誤點期間只通知一次，到站或離站後才重新允許下次通知）
  • 公車用「預估到站秒數」本身是否小於 notifyBeforeMinutes 判斷；台鐵／捷運用「誤點分鐘數」是否超過 delayThresholdMinutes，或快到站時用到站時間判斷

/tools/transit/timetable 時刻表查詢

  • 選運輸工具＋站／路線＋日期 → 即時打對應 TDX 時刻表 API → 列表顯示，不快取即時到站資料，但時刻表這類低變動資料可以快取一整天
  • 可以從查詢結果直接「加入監控」，帶入 /tools/transit/routes/new 的對應欄位，不用重新輸入

開發順序

  1. 完成 TDX 帳號申請＋OAuth2 token 取得與刷新機制（lib/tdx-client.ts）
  2. 完成（部分） 時刻表查詢頁已串台鐵／高鐵／公車真資料（app/api/transit/**），捷運因 LiveBoard 覆蓋不穩定仍用示範資料
  3. 監控路線 CRUD（CommuteRoute）——目前頁面還是示範資料，尚未接到資料庫
  4. 通知管道設定（Telegram chatId 綁定）——頁面是示範資料，尚未真的串 Telegram Bot API
  5. 背景輪詢 endpoint＋排程串接＋推播邏輯
  6. 總覽頁改接真資料（目前總覽／監控路線頁的即時狀態都還是 lib/transit-mock-data.ts 的示範資料，只有時刻表查詢頁換成真資料）

待確認／未來可擴充項目

  • 通知管道選擇：目前建議 Telegram Bot API（LINE Notify 已於2025年3月終止服務，改用 LINE Messaging API 門檻較高）；若之後想用 LINE 或網頁推播（Web Push）再擴充 NotificationChannel.provider
  • 要先確認實際通勤會用到的捷運系統是否支援 TDX 的 LiveBoard 即時到離站，不支援的話該路線只能做時刻表查詢，不能做即時提醒
  • 排程方案：Vercel Cron、或自架排程打內部 API，待實際部署環境決定
  • 歷史準點率統計／延誤分析：這次規劃的範圍只有查詢與即時提醒，不包含統計功能，先不做
  • 多人共用某條監控路線（例如同事共用上班路線設定）：目前設計是每個使用者各自的 CommuteRoute，不共用，之後有需求再評估
