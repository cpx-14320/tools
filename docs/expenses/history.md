## 四、看不懂 / 容易誤會的地方

### F1. 新帳號直接看到別人的 OpenAI API Key ✅ 已修正（2026-11-05）

**原本的問題**：打開「顯示 AI 記帳入口」後，一個**剛註冊、什麼都沒設定過**的帳號，
設定頁就顯示 `OpenAI API Key  sk-***XYZ`，AI 記帳彈窗也寫「已設定 API Key，點這裡更換」。

原因：金鑰存在瀏覽器的 `localStorage`，鍵是固定的 `cpx-tools:expenses:openai-key`，
**不綁帳號**。所以同一台瀏覽器換帳號登入，會直接繼承前一個帳號留下的金鑰。

**修正內容**：

- `components/expenses/ai/use-ai-key.ts` → `.tsx`，鍵改成
  `cpx-tools:expenses:openai-key:<userId>`，一個帳號一格。
- 新增 `AiKeyScopeProvider`，由 `components/expenses/expenses-shell.tsx` 包住整個記帳本；
  `app/tools/expenses/(workspace)/layout.tsx` 用 `getSessionUser()`（已經有 `cache()`，
  不會多一次查詢）把 userId 傳下來。
- 不知道是誰（SSR、沒登入）時一律當作「沒有金鑰」，而且寫入會被忽略——不會再退回
  那個共用的鍵。
- 舊的共用鍵在載入時直接刪掉。**刻意不把它搬進目前登入者的格子**：沒辦法知道當初是誰
  貼的，搬過去等於把別人的金鑰正式發給這個帳號。代價是原本設過的人要重貼一次。

**驗證**：`cpx14320` 存入測試金鑰 → localStorage 只出現
`cpx-tools:expenses:openai-key:6aec90dd…` 一格 → 登出、另開帳號 `cpx14321` →
顯示「尚未設定」→ 再登回 `cpx14320` → 金鑰回來。舊的共用鍵確認已消失。

> 補充：測試過程中發現金鑰彈窗寫著「目前還在接模型，先用**模擬解析**跑整套流程」，
> 所以現階段就算繼承了金鑰也不會真的送出去。但金鑰本身仍然被下一個帳號看得到、
> 之後接上真模型就會變成實際的扣款風險，所以還是修掉。

> 還擋不住的：同一台瀏覽器、同一個帳號登入的人仍然看得到那一把。localStorage 本來就是
> 跟著「這台瀏覽器 + 這個帳號」走，要再往下擋就得改成不落地（每次用才問），那是另一個
> 取捨，目前沒動。

> 以下是原本的問題描述，留著當背景。

#### 情境一：剛註冊，還沒設過任何預算

新帳號第一次進首頁，往下捲就看到這一塊（這是實際截到的畫面）：

```
本月收支
  收入  NT$ 0        支出  NT$ 890        ← 這是這個月真的花掉的錢

預算支出                          查看全部
  NT$ 0 / NT$ 0        剩 26 天    0%     ← 總結這一行
  🍴 餐飲      NT$ 448   未設定
  🧺 日用品    NT$ 342   未設定
  🍰 零食      NT$  68   未設定
  🚌 大眾交通  NT$  32   未設定
```

新用戶看到的矛盾：

1. 標題寫「預算**支出**」，大字卻是 `NT$ 0`，可是上面才剛說支出 890。
2. 進度 `0%`、`剩 26 天`，看起來像「這個月還沒開始花」。
3. 但下面四列清清楚楚列著 448 / 342 / 68 / 32，加起來正好就是 890。

也就是**同一張卡片裡，上面說 0、下面說 890**。真正的意思是「你還沒設任何預算，
所以沒有可以算的分母」，但畫面一個字都沒提。`剩 26 天` 更會誤導——它讓人以為
這條 0% 的進度條是有在跑的，只是你還沒花到。

> 這裡最怪的是「未設定」三個字的位置。它緊貼在金額右邊（`NT$ 448  未設定`），
> 乍看像是在描述那個金額，新用戶會以為是「這 448 還沒分類好」之類的意思，
> 而不是「這個分類沒有設預算」。

#### 情境二：只幫「餐飲」設了預算 5,000

接著我去設定頁幫餐飲設了每月 5,000，回首頁變成：

```
本月收支
  收入  NT$ 45,000    支出  NT$ 1,457    ← 真的花掉 1,457

預算支出                          查看全部
  NT$ 563 / NT$ 5,000  剩 26 天   11%    ← 只算餐飲
  🍴 餐飲      NT$ 563 / NT$ 5,000  11%
  🧺 日用品    NT$ 342   未設定
  🍰 零食      NT$  68   未設定
  💬 其他      NT$  62   未設定
```

這下子**同一個畫面上有兩個「我花了多少」的數字：1,457 和 563**，而且相差超過兩倍。

新用戶的反應會是：

- 「我到底花了 1,457 還是 563？」
- 「563 是不是扣掉什麼了？」
- 「下面明明列著 342、68、62，為什麼上面那行只算 563？」

實際規則是「總結那一行只加總**有設預算的分類**」，563 就是餐飲一個分類的數字。
問題在於下面的清單把「有設預算的餐飲」跟「沒設預算的日用品／零食／其他」
**混在同一張卡、同一個清單裡**，視覺上看起來它們都歸那條 11% 的進度條管。

#### 為什麼會造成實際的誤判

假設一個人只幫「餐飲」設了 5,000 的預算，這個月：

| 分類 | 花費 | 有設預算？ |
| --- | --- | --- |
| 餐飲 | 4,800 | ✅ 5,000 |
| 電商購物 | 12,000 | ❌ |
| 娛樂 | 3,000 | ❌ |

首頁會顯示：

```
支出        NT$ 19,800
預算支出    NT$ 4,800 / NT$ 5,000   96%
```

96% 看起來「還在預算內、快到了但沒爆」，但這個月其實花了快兩萬。
**一個只設了一個分類預算的人，會被這張卡片安慰。** 這是真正的風險所在。

#### 建議

- 總結那一行的標題講清楚範圍，例如「**已設預算的分類** NT$ 563 / NT$ 5,000」。
- 把「未設定」的分類移出這張卡，或至少用分隔線 + 小標（例如「尚未設定預算」）
  跟上面分開，不要讓它們看起來屬於同一條進度條。
- 一個預算都沒設時，不要畫 `NT$ 0 / NT$ 0 ・ 0% ・ 剩 26 天`，直接換成空狀態，
  例如「還沒設定任何預算，點這裡幫常花的分類設一個」。
- 「未設定」改成灰色的次要標籤並換行，或直接寫「未設預算」，不要貼在金額旁邊。

### F3. 「轉帳明細 › 查看更多」是一顆永遠不會動的按鈕 ✅ 已修正（2026-11-05）

**原本的問題**：`assets-view.tsx` 直接寫死 `disabled`。雖然註解說「不要給一顆點了沒反應
的連結」，但它仍然畫在那裡、看起來就是連結，只是灰的。新用戶會一直點。

**修正內容**：把整顆按鈕拿掉，標題列只剩「轉帳明細」。之後真的做了「看更久以前的轉帳」
再加回來。

> 還沒修：同一區的空狀態文案寫「還沒有任何轉帳紀錄，**點右上角的圖示**新增」，
> 但轉帳按鈕（⇄）其實在**右下角**的浮動鈕。文案指錯方向。
> （預設資料一定會建一筆轉帳，所以這段文案平常看不到。）

### F4. 轉帳選到同一個帳戶時，會默默清掉另一欄

### F5. 支出的子明細顯示成綠色的「＋」

一筆 −NT$ 120 的支出，展開後子項目長這樣：

```

  紅茶                   +NT$ 40   ← 綠色
```

### E1 詳細情境：「＋ 新增明細」會把已經輸入的金額清掉 ✅ 已修正（2026-11-05）

**修正內容**（`components/expenses/transaction-modal.tsx`）：點「＋ 新增明細」時，
把已經輸入的金額直接帶成**第一筆明細的金額**，鍵盤也停在那一項。使用者只要補一個
名稱就好，不用重打數字。

```
打了 120 → 點「＋ 新增明細」
  明細                    淨額 NT$ 120   ← 不再歸零
    ┌────────────────────────┐
    │ （名稱待填）            │ 刪除
    │ [加項][扣項]  NT$ 120  │           ← 金額已帶入
    └────────────────────────┘
  明細：第 1 項
  NT$ 120                                ← 鍵盤直接停在這一項
```

`amountExpr` 本身不動，所以按「移除全部明細」仍然會退回原本打的那個算式。
金額是空的或算式還沒算完（例如 `120+`）時，照舊從 0 開始。

> 以下是原本的問題描述，留著當背景。

#### 這個功能是什麼

「明細」是把**一筆**消費拆成幾個小項。例如早餐買了三明治 80 + 紅茶 40，
你想記成一筆 120 的「早餐」，但又想留下裡面是哪兩樣東西。

#### 實際操作，一步一步

新用戶最自然的順序是「先打金額，再想要不要拆」：

| 步驟 | 動作 | 畫面 |
| --- | --- | --- |
| 1 | 點 ＋ 開「新增收支紀錄」 | `NT$ 0`，儲存是灰的 |
| 2 | 選「餐飲 › 早餐」 | 下方提示「這個分類還要再選一個項目」 |
| 3 | 用數字鍵盤打 `120` | `NT$ 120`，**儲存變成可按** |
| 4 | 選帳戶「現金錢包」、備註打「測試早餐 三明治+紅茶」 | 都正常 |
| 5 | 想順便記一下裡面有什麼，點「**＋ 新增明細**」 | ⚠️ **`NT$ 120` 瞬間變回 `NT$ 0`** |

第 5 步之後的畫面：

```
明細                          淨額 NT$ 0     ← 剛剛的 120 不見了
  ┌──────────────────────┐
  │ 例如：底薪            │  刪除
  │ [加項][扣項]  NT$ 0   │
  └──────────────────────┘
  ＋ 新增明細項目        移除全部明細

明細：第 1 項
NT$ 0                                      ← 鍵盤也歸零了
…
明細的名稱跟金額都要填          取消  [儲存]  ← 儲存又變灰了
```

沒有任何提示說「金額會改由明細加總決定」。使用者只看到自己剛打的 120 消失、
原本可以按的儲存又變灰了。

#### 為什麼這很痛

1. **沒有警告。** 不是彈窗問「要改成用明細算嗎？」，是直接清掉。
   （更正：當時我寫「點『移除全部明細』也不會把 120 還回來」，這點是錯的——
   `amountExpr` 其實一直留著，移除全部明細會退回 120。真正的問題只在於拆明細的
   過程中金額無聲歸零。）
2. **金額愈長愈痛。** 早餐 120 重打還好；如果是一筆 `15,800` 的旅遊費用打完才想拆，
   等於整串重來。
3. **它在整個表單的最後面。** 「＋ 新增明細」在備註下面，使用者是**一路填到底**
   才會碰到它——也就是說，被清掉的那個金額是在好幾步之前輸入的，距離遠到不會
   立刻聯想「是剛剛那一下把它清掉的」。第一反應通常是「咦？我剛剛有打嗎？」
4. **它懲罰了比較用心的使用者。** 只想記總額的人不會碰到；願意多花力氣拆明細的人
   反而被罰重打一次。

#### 補充：明細區的其他小問題

- **空白明細的提示文字是收入的例子。** 在「支出」模式下，明細名稱欄的 placeholder
  寫「例如：**底薪**」。底薪是收入，記早餐的人看到這個會愣一下。支出應該是
  「例如：主餐」「例如：飲料」之類。
- **「加項／扣項」對新用戶是新名詞。** 而且這個概念會漏到顯示層——存檔後在帳戶明細
  展開那一筆，會看到綠色的「＋NT$ 80」掛在一筆紅色的 `−NT$ 120` 底下（見 F5）。

#### 建議

照「傷害由小到大」排：

1. **最小修正**：點「＋ 新增明細」時，把原本的金額自動帶成第一筆明細的金額
   （名稱留空讓使用者填）。120 → 第 1 項 `NT$ 120`，淨額仍是 120，儲存維持可按。
   使用者只要補名稱、再按「＋ 新增明細項目」加第二項就好。
2. **或者**：保留原金額當作「尚未分配」，明細填到一半時顯示
   「已拆 80／共 120，還差 40」，這樣也順便解決了「拆到一半金額對不起來」的問題。
3. **至少要有提示**：如果真的要清空，換成一行說明
   「改用明細後，金額會由下面的項目加總決定」，不要讓數字無聲消失。

## 六、做得好的地方（建議保留）

- **帳戶「對帳」流程**：先講清楚「差額會自動補成一筆調整紀錄，不用回頭翻整份紀錄」，

  ＋ 真正的垃圾桶可還原。而且沒有用瀏覽器原生 `confirm()`。
- **固定收支的「待確認」設計**：不是直接硬塞一筆進帳，而是列出「待確認 1 筆」讓你

  不看你有多少錢」的設計理由，全部講清楚。

# 八、新增／刪除／編輯／還原的行為對照

> 記在這裡的原因：這幾個資料之間互相牽連（分類→交易、帳戶→交易／轉帳／目標／固定收支），
> 「刪了 A 又還原 B」的組合會隨著欄位變多而爆炸。與其每次都重想一遍，不如把規則寫死在
> 這張表上，之後加新欄位只要回來對一次。
>
> 最後驗證：2026-11-10

## 8.1 三條共用規則

**規則一：刪除一律先問，文案依情境加碼。**
不分「乾淨的」或「還有紀錄在用的」——以前是刪得掉的不問、刪不掉的才問，剛好跟直覺相反。

**規則二：刪除是搬進垃圾桶，不是消失。**
垃圾桶不會自動清空。「一次刪除＝一次還原」：主分類連同子分類、預算規則存成**同一個**
垃圾桶項目，不會出現「分類回來了但預算沒回來」這種半套狀態。

**規則三：刪除時盡量不去改動「指向它的人」。**
因為那樣從垃圾桶還原回來就接不回去了。唯一的例外是**會繼續產生新壞資料**的情況
（見 8.4 的轉帳型固定收支）。

## 8.2 order（排序編號）的規則

| 動作 | 行為 |
| --- | --- |
| 新增 | `order` = 同一層目前最大的 ＋ 1，所以一定排在最後 |
| 刪除 | 不重新編號，序列會留洞（0,1,2,**4**,5…） |
| 排序 | 整層重寫成 0,1,2,…，**洞會在這時候補平** |
| 還原 | 原位還空著 → 回原位；被佔走了 → 排到最後 |

- **為什麼新增不能用「目前有幾筆」當 order**：刪過之後筆數小於最大編號，新的那筆會跟
  既有的撞號、排序並列，位置由資料庫決定——症狀就是「刪掉飲料再新增，它沒排到最後」。
- **為什麼還原要分兩種**：刪錯了馬上還原是最常見的情況，那時候原位就是一個洞，放回去
  等於什麼都沒發生，這才是「還原」該有的樣子；但刪掉之後又排序過的話原位已經是別人的，
  硬插回去就是撞號。
- **為什麼刪除不順手重新編號**：還原時原本的 `order` 就接不回去了，而且使用者刪完特地
  排過的順序會被推走。
- 系統分類（手續費、未分類）不參與排序，位置固定在最後。

## 8.3 分類

### 主分類
| 動作 | 行為 |
| --- | --- |
| 新增 | 排到最後（見 8.2） |
| 編輯 | 名稱、圖示、顏色、預設帳戶、預算。子分類的圖示／顏色跟著主分類走，不單獨存 |
| 刪除 | 連同**子分類＋預算規則**一起進同一個垃圾桶項目；底下的交易與固定收支改掛「未分類」，**而且會記下是從哪一個分類搬過去的** |
| 還原 | 主分類、子分類、預算規則一起回來；被改掛到未分類的那些紀錄**回到原本的子分類** |

- **為什麼要記下搬過去的是哪幾筆**：未分類裡面混著各種來源的紀錄，沒有這份清單的話，
  還原分類之後根本分不出哪幾筆該搬回來。

### 子分類
| 動作 | 行為 |
| --- | --- |
| 新增 | 收支類型、圖示、顏色一律跟父分類 |
| 刪除 | 底下的交易改掛「未分類」（不是改掛到父分類） |
| 還原 | 父分類還在 → 回到父分類底下；父分類已經不在 → 見 8.5 |

- 主分類底下有子分類時，錢要記在子分類上（`needsSubcategory`）——記在殼身上的話，報表
  展開那個主分類時那筆錢在每個子分類裡都找不到。

### 還原時撞名
現有清單裡已經有同名的分類時，會**先跳一個彈窗**列出「原名 → 新名」（例如
`飲食 → 飲食(1)`），確認後才還原。批次還原**只跳一個彈窗**、一次列出全部會改名的——
十項裡三項撞名就跳三個長得一樣的彈窗，只會讓人直接亂按。

## 8.4 帳戶

| 動作 | 行為 |
| --- | --- |
| 新增 | 需要帳戶類型與起始金額 |
| 編輯 | 名稱、類型、起始金額 |
| 刪除 | 只刪帳戶本身，**不去改動指向它的任何資料**；有東西掛著時先擋下來並列出後果 |
| 還原 | 帳戶一回來，上面那些參照**自動全部接回去** |

刪除前的確認會**一行一種**列出後果（全部混成「還有 N 筆紀錄」的話，被暫停的固定收支
跟一筆會變成「不指定」的交易，嚴重程度差很多卻看不出來）：

| 掛在帳戶上的東西 | 刪除後 |
| --- | --- |
| 交易 | 變成「不指定帳戶」，紀錄本身留著 |
| 轉帳 | 留著，其中一端顯示「已刪除帳戶」 |
| 分類的預設帳戶 | 失效（記帳時不再自動帶入） |
| 綁定帳戶的存錢目標 | 進度變成 0 |
| 轉帳型的固定收支 | **會被暫停** |

- **為什麼只有轉帳型固定收支要動手**：其他參照都只是「顯示不出帳戶」，救回帳戶就自動
  接回去。但轉帳規則會**繼續產生新的壞資料**——每一期生出一筆轉到不存在帳戶的轉帳，
  而那些錢不會進任何帳戶的餘額，等於默默蒸發，使用者完全沒有徵兆。
- **為什麼是暫停不是刪除**：帳戶還原回來之後自己按一下恢復就好（卡片上看得到「已暫停」）。
- 轉出或轉入對不到帳戶的轉帳，可以在**資產頁 › 轉帳明細**用「對不到帳戶 N」那顆篩出來
  （只有真的存在時才會出現，而且不吃日期範圍、整份找）。

## 8.5 還原時「指向的東西已經不在」

還原不是把文件原封不動塞回去——它指向的東西可能已經被刪掉了。這類清理走
`trash.server.ts` 的 `REF_FIELDS` 一張表，**不逐一判斷組合**：

| 文件 | 欄位 | 指向的東西不在時 |
| --- | --- | --- |
| 交易 | `accountId` | 拿掉（變成不指定帳戶） |
| 交易 | `categoryId` | 改掛「未分類」（必填，清掉會變成壞資料） |
| 固定收支 | `categoryId` | 改掛「未分類」 |
| 固定收支 | `linkedGoalId` | 拿掉 |
| 分類 | `defaultAccountId` | 拿掉 |
| 存錢目標 | `accountId` | 拿掉 |
| 預算規則 | `categoryId` | 改掛「未分類」 |

**刻意不收進這張表的**：轉帳的轉出／轉入帳戶、轉帳型固定收支的兩個帳戶。那種斷掉只是
顯示不出名字（畫面上就是「已刪除帳戶」），把帳戶從垃圾桶救回來它就自己正常了——硬清掉
反而接不回去。

> 判斷標準：**會不會把壞資料往前傳**。分類的預設帳戶指向死帳戶，之後每次用這個分類記帳
> 都會預選那個死帳戶；固定收支的 `linkedGoalId` 指向不存在的目標，每期入帳都會做一次
> 沒有作用的加總而且毫無徵兆。這兩種要清。只是顯示不出名字的不用。

## 8.6 系統分類

| 分類 | 角色 | 限制 |
| --- | --- | --- |
| 手續費 | 轉帳填了手續費時，那筆支出記在這裡 | 不能刪除、不參與排序、固定排在未分類前面 |
| 未分類 | 刪掉分類時收容底下紀錄的地方 | 不能刪除、不參與排序、固定排在最後 |

- 兩者都用**旗標**辨識（`isFee` / `isUncategorized`），不是比對名稱——使用者把它改名之後
  還是同一個分類，不會再被自動建出第二個。
- 判斷一律走 `isSystemCategory()`，不要在畫面各處各寫一次：系統分類從一種變成兩種時，
  散在十幾處的判斷漏掉一處，那裡就會出現一顆刪得掉的「手續費」。
- 手續費是**第一次真的記到手續費時才建**，不會預先塞給每個帳號。

## 8.7 其他連動

| 刪除的東西 | 連帶行為 |
| --- | --- |
| 存錢目標 | 連著它的固定收支規則會解除連動（`linkedGoalId` 拿掉）。**這個副作用刻意不記進垃圾桶**——還原目標之後要不要重新連動是使用者的決定，自作主張接回去會讓一條他已經改過的規則突然又開始存錢 |
| 轉帳（有手續費） | 手續費那筆支出跟著進**同一個**垃圾桶項目。分成兩項的話可能只還原一邊，帳就不平了 |
| 帳戶類型 | 底下還有帳戶就擋下來，要先把帳戶改成別的類型 |
| 固定收支規則 | 已經入帳過的交易／轉帳是獨立快照，不受影響（規則改金額、暫停、刪除都一樣） |


## 8.8 操作面的規則（2026-11-11 補，2026-11-13 更新）

| 項目 | 行為 |
| --- | --- |
| 排序／選取那一列 ＋ 選取工具列 | 捲動時一起釘在卡片頂端（`StickyToolbar`）。右邊只有一兩顆按鈕的頁面（帳戶類型、存錢目標）**把標題也放進同一列一起釘**——標題獨佔一列、按鈕那列左邊整片空著，等於白白多墊高一截。有分頁切換（支出／收入）的頁面則維持標題在外面，不然釘住的部分會變兩列 |
| 工具列與上下的間距 | 由 `StickyToolbar` 自己的 `py-3` 決定（上下各 12px）。它用 `-my-4` 把呼叫端 `gap-4` 的上下留白吃掉——不然 16px gap 疊上自己的內距，一列按鈕的區塊會佔掉快一百 px |
| 選取工具列 | **固定一列**：左邊「全選 ・ 已選 N 項」，右邊「修改帳戶／修改分類／刪除」 |
| 退出選取模式 | 只有上面那顆「選取 → 取消」（`SelectionToggle`）。它寫**取消**不是「完成」：它做的事就是退出、清掉勾選，寫「完成」會被讀成「把剛剛選的送出去」，按下去卻什麼都沒發生。工具列右邊原本還有一顆同樣寫「取消」的按鈕，兩顆字一樣、做同一件事，已經移除 |
| 排序模式的「完成」 | **維持「完成」**：排序每按一次箭頭就已經存檔，離開時沒有東西可以取消。跟選取那顆長得一樣但字不同，是因為它們真的不一樣 |
| 待套用（挑好目標還沒送出） | 也是一列：左邊「修改分類：→ 零嘴 › 甜食 ・ 已選 N 項」，右邊「**重選**／完成」。左邊那顆不叫「取消」：上面那顆退出選取模式的已經叫取消，同一畫面兩顆一樣的字做不同範圍的事，使用者只能靠位置猜；它做的是「放掉這次挑的目標、回去重挑」，勾選的項目留著，所以寫重選。「完成」是整條列上唯一實心的按鈕，真的會動資料 |
| 進行中的回饋 | **只用共用的處理中遮罩**，按鈕文字不換成「處理中…」。以前有的按鈕會變字、有的不會，同一個 app 兩種回饋方式會讓人懷疑沒變字的那顆是不是沒按到 |
| 提示文案 | 批次改完說「N 筆已改為「X」」，不是「已改好 N 筆，改成 X」 |
| 系統分類（未分類、手續費） | 選取模式下**兩個都不能勾**，整張卡淡化（跟排序模式同一個處理）。它們刪不掉，勾得起來卻刪不掉等於讓人白勾一輪、按了刪除才被打回票。手續費本來為了批次「修改帳戶」開放勾選，但「可以勾」在這份清單上就代表「可以一起刪」，為了一個很少用的批次動作讓系統分類混進刪除範圍並不划算——要改它的預設帳戶，點那一列進編輯彈窗一樣改得到 |
| 「處理中」遮罩 | 刪除、批次修改、**還原**（垃圾桶裡的還原、刪除後提示上的「復原」）、永久刪除都會出現；共用 `useBusy()` |
| 最近刪除彈窗 | 關閉（X、「關閉」、點背景）時清掉勾選，下次打開是乾淨的 |
| 資產頁 › 轉帳明細 | 有對不到帳戶的轉帳時才會出現「對不到帳戶 N」篩選，整份找、不吃日期 |
| 卡片裡面的工具列 | 帳戶明細頁的「明細」區走 `StickyToolbar` 的 `inCard` 版本（白底、照卡片的 16px 內距）。那張卡要拿掉 `overflow-hidden`——它會讓裡面的 `position: sticky` 失效（瀏覽器改以那張卡當捲動參考，而卡片自己不捲動），所以那條列以前**從來沒有真的釘住過**；圓角改由工具列自己的 `rounded-t-2xl` 接住 |

## 8.9 驗證紀錄（2026-11-11，`scripts/.lifecycle.mts` 用伺服器端函式直接跑）

全部通過。每一條都是「建 → 刪 → 還原」之後檢查資料，測完的資料會自己清掉。

**交易**
- 刪除 → 還原：帳戶與分類都回來
- 交易在垃圾桶期間它的分類被刪掉 → 還原交易改掛「未分類」

**帳戶**
- 刪帳戶不動交易（`accountId` 保留，明細頁的「未指定帳戶」篩選把這種也算進去）
- 還原帳戶後交易自動接回，不需要任何搬移

**轉帳（含手續費）**
- 手續費那筆支出：建立轉帳時產生、刪轉帳時一起消失、還原時一起回來
- 轉帳本身還原且 `fee` 保留

**存錢目標**
- 刪目標 → 連著的固定收支解除連動
- 還原目標：帳戶綁定保留；固定收支**不會**自動接回連動（刻意，見 8.7）
- 綁定的帳戶被刪 → 進度顯示 0；還原帳戶 → 進度恢復

**固定收支**
- 支出規則刪除 → 還原：略過的期數（`skippedDates`）保留
- 轉帳規則刪除 → 還原：兩端帳戶與手續費保留
- 刪掉轉入帳戶 → 轉帳規則被暫停；還原帳戶後**仍是暫停**（要自己按恢復，刻意）

**前面幾節已驗證過的**（見 8.2–8.5）：order 的四種情況、撞名改名的單筆與批次彈窗、主分類連同子分類＋兩種預算一起還原、分類的預設帳戶被刪後還原會清掉、刪帳戶時固定收支與目標會被算進「還有東西掛著」。

# 九、功能回歸測試腳本（2026-11-12）

> 這節回答的是「每次改完程式碼，怎麼知道有沒有改壞別的功能」。

## 9.1 `scripts/expenses-feature-check.mts`

直接呼叫 `lib/expenses/*.server.ts` 的函式（跟 API route 背後用的是同一份邏輯），不透過
HTTP，也不用開著 `npm run dev`。會在 `users` collection 裡建一個**真的**測試帳號
（`qa-expenses-check-<時間戳記>`，密碼用 bcrypt 雜湊、拿到跟真的註冊一樣的預設工具權限，
跟 `lib/auth.ts` 的 `createUser` 同一套邏輯），模擬「剛註冊的新帳號」，依序跑過：

- 新帳號第一次進記帳本的預設資料（`seedExpensesPresets`，含重複呼叫不會建兩份）
- 分類：新增／子分類／重複名稱擋下／編輯／排序／刪除還原／強制刪除改掛未分類後還原
- 帳戶類型／帳戶：新增／刪除類型被帳戶擋下／刪帳戶再刪類型／還原
- 交易：新增／拆明細（加項－扣項＝淨額）／編輯／刪除還原（含垃圾桶的分類路徑快照）
- 轉帳：手續費自動建交易／改 0 自動刪除／刪轉帳連手續費一起進垃圾桶再一起還原
- 預算：設定／同月同分類覆蓋不疊加／刪除

# 十、主視覺的角色對話（OS 泡泡）

> 首頁主視覺上那顆白色對話框。程式在 `lib/expenses/pet-os.ts`（判斷＋句子池）跟
> `components/expenses/pet-os-bubble.tsx`（顯示＋輪播）。

## 10.1 它在做什麼

**不是報表，是「替使用者講出他心裡那句話」。** 句子刻意不帶數字——數字在底下的卡片裡
已經寫得很清楚了。所以判斷只決定**抽哪一池句子**，不決定講得多精確。

## 10.2 七種狀態與觸發條件

判斷的時間窗是**近 7 日 vs 前面同樣長的 7 日**（`OS_WINDOW_DAYS`）。7 天是因為消費習慣
以週為單位循環（週末花得多），拿 7 比 7 才對得起來。

| 狀態 | 觸發條件 | 門檻常數 |
| --- | --- | --- |
| `idle` | 近 7 日**一筆紀錄都沒有**（這時直接回傳，其他都不判斷） | — |
| `overBudget` | 本月已用預算比例 > 月進度 ＋ 15%（月初過一半卻花了 65%） | `budgetAheadBy: 0.15` |
| `spike` | 近 7 日支出 ≥ 前 7 日的 1.5 倍，且近 7 日 ≥ 1000 | `spikeRatio`／`spikeMinAmount` |
| `bigTicket` | 近 7 日單筆最大 ≥ 該期間總支出的 40%，且 ≥ 2000 | `bigTicketShare`／`bigTicketMinAmount` |
| `income` | 近 7 日有收入，而且比前 7 日多 | — |
| `saving` | 近 7 日支出 ≤ 前 7 日的七成**，且上面三種支出狀態都沒中** | `savingRatio: 0.7` |
| `calm` | 以上都不符合 | — |

門檻全部集中在 `OS_THRESHOLDS`，調整不用翻程式。

**為什麼每個條件都要再加一個絕對金額門檻**：比例自己會騙人。從 80 變 200 也是 2.5 倍，
但那不是一件值得講話的事；花 300 塊的那天隨便一筆都佔 40%。

## 10.3 同時符合好幾種狀態時：把句子池合起來抽，不排優先序

這幾個狀態本來就會同時成立（這個月預算超前、同時這週又有一筆大額支出）。硬排優先序的話，
排在後面的句子幾乎永遠不會出現，等於白寫。所以是 `moods.flatMap(m => LINES[m])` 全部合起來
再洗牌。

唯一的例外是 `saving`：「花得少」跟「花得多」不可能同時成立，所以只有前面三種支出狀態
都沒中時才看它。

## 10.4 為什麼 seed 要從伺服器傳下來

首頁是 Server Component，**伺服器算一次、瀏覽器 hydrate 時再算一次**，兩邊各自
`Math.random()` 就會抽到不同句子 → hydration mismatch，畫面還會閃一下。所以 `page.tsx`
產生一個 seed 當 prop 傳下來（`newOsSeed()`），同一次請求兩邊用同一個 seed，結果一致；
每次重新整理都是新 seed，「每次進來換一批」仍然成立。

## 10.5 顯示規則

| 項目 | 行為 |
| --- | --- |
| 輪播 | 一句停 15 秒（`HOLD_MS`），淡出 400ms → 換字 → 淡入 400ms |
| 換字方式 | 先降透明度到 0 再換字，不是換完才淡入——後者等於硬切，淡入只是多一層 |
| 只有一句時 | 不啟動計時器（轉場只會讓同一句話自己閃一下） |
| 計時器 | 用 `setTimeout` 重新排下一次，不用 `setInterval`（分頁切到背景再回來會一次補跑好幾輪） |
| 版面 | 框水平置中、**框裡的字靠左**（換到第二行時置中會讓兩行左緣對不齊，讀起來像標語不像在講話） |
| 寬度 | `max-w-[260px]`，所以一句話實際上最多兩行 |

| 清除預算 | 把選到的分類設過的每一筆都刪掉（紅字那顆，走 `ConfirmModal`） |

- **月份共用、金額一列一個**：一批一起改本來就是同一個生效月份；金額則每個分類差很多
  （房租 15000、飲料 1200），共用一個數字的批次多數時候用不到。原本規劃的「從某個月起
  套用」（只改日期不改金額）跟「批次設同一個金額」因此併成這一個彈窗——後者變成彈窗上方
  的「全部設成同一個金額 ＋ 一次填入」，填完還能單獨改其中一兩列。
- 每一列**預先帶入該分類目前生效中的金額**；**空著＝這次不改它**（不是改成 0，0 是
  「不編預算」）；**跟現在一樣的金額不會寫出去**，否則歷程會多一列跟上一列一模一樣的數字。
- 選取模式中，分類底下那幾列歷程**只當資訊看**（不能點進單筆編輯、不顯示「刪除」）：
  這時候該做的是挑分類，點進去會把勾好的一批丟在半路。
- 批次寫入是**逐筆依序送**，不是 `Promise.all`：每一筆的回應都是「完整的規則清單」，
  併發的話幾個回應會互相覆蓋。
- 改版前存在分類身上的舊預算（legacy）資料庫裡沒有文件可以刪，清除時改成**補一筆金額 0**
  蓋掉它，不然清完它會原地復活。
- 踩到的坑：`fieldInputClass` 裡有 `w-full`，再加 `w-28` 不會贏（看 CSS 產出順序），
  輸入框撐滿整列把分類名稱擠成 0 寬——要寫 `w-28!`。另外兩個彈窗同層、關閉時的 `key`
  都寫 `"closed"`，React 會噴「兩個小孩用同一個 key」。

### 報表：自訂比較年月（2026-11-15）

- `CompareMode` 多一個 `"custom"`，`CompareSetting` 多一個 `yearMonth?`（沒給就當上個月）。
- 語意是**把現在看的這段整個平移到挑的那個年月**，不是自己選一段起訖區間：平移才保證

  天／週／近三個月／近六個月平移基準日、自訂區間兩端各平移同樣月數。

  年模式挑到同一年）就**不比較**，按鈕也跟著寫「不比較」——本來算不出可比區間時，畫面上
  一個徽章都沒有、按鈕卻寫著「vs 2026 年」，看起來像比完了全部持平。

合併過來，重點是**名稱（備註）判得更準、關鍵字真的配得到分類**。

**最大的一個洞：字典寫的分類名稱是舊的。** 預設分類改版後叫「飲食／住家／美妝保養／

新帳號等於整本字典有一半配不到任何分類，解析出來大多是未分類。現在每一條的候選名稱

| 輸入 | 以前 | 現在 |
| --- | --- | --- |
| 午餐全家便當100 | 全家（超商）先中 | 飲食 › 午餐 |
| uber eats 晚餐 250 | 可能中到 uber → 計程車 | 飲食 › 晚餐 |
| 全聯買菜 486 | 日用品 | 飲食 › 食材 |

因為它要參與重疊比對（「全家便當」才不會被拆成「全家」）。

**名稱（備註）改成按位置扣掉金額**，不是把所有數字都刪掉：

| 輸入 | 以前的名稱 | 現在的名稱 |
| --- | --- | --- |
| 7-11買東西50 | `-買東西` | `7-11買東西` |

### 2026-11-16：孵化動畫遺漏的原因與修法（已查清，先不執行）

**現象**：餵食把等級從 9 級以下餵到 10 級以上的那個當下，角色畫面上還是一顆蛋，沒有
播孵化動畫；要重新整理頁面，蛋才突然變成孵化後的角色。

**原因**：孵化的判斷（`maybeHatch`：把造型換成孵化後的預設套裝、回傳 `justHatched`）
只寫在 `settlePetRewards()` 裡，而那支函式**只在進頁面時跑一次**（`pet/page.tsx` 的
`expensesPetState()`）。餵食是另一條路 `feedPet()`，只做 `$inc xp` 跟扣庫存，從來沒呼叫
`maybeHatch`。所以：
- 餵食當下：等級算出來已經 10 級，但資料庫裡的 `outfitId` 還是蛋、`justHatched` 這次
  回應也沒有這個欄位（`feedPet` 的 `toDTO(updated)` 沒傳 `justHatched` 參數），前端的
  `pet-view.tsx` 完全不知道「這次跨過孵化線了」，角色畫面維持蛋。
- 重新整理：`pet/page.tsx` 重新呼叫 `expensesPetState()` → `settlePetRewards()` → 這次
  `maybeHatch` 判斷等級已經 ≥10 且 `claimedKeys` 還沒有 `"hatched"`，於是換裝、回傳
  `justHatched: true`；`pet-view.tsx` 的 `useState(initialPet?.justHatched ? "hatching" : "idle")`
  是在**掛載當下**讀這個值，所以重新整理（＝重新掛載）才看得到孵化動畫。
- **「一直餵食可能也會錯過動畫時間」的疑慮也成立**：孵化判斷用 `claimedKeys` 當冪等
  開關，一旦某次 `settlePetRewards` 真的執行過 `maybeHatch`（例如使用者剛好在跨過等級
  之後、動畫觸發之前就重新整理了一次），`"hatched"` 這把 key 就寫進去了，之後不管再
  重新整理幾次，`maybeHatch` 都會因為 `pet.claimedKeys.includes(HATCHED_KEY)` 而直接
  回傳 `false`——動畫的「正確觸發窗口」只有「跨過等級之後、下一次 `settlePetRewards`
  執行之前」這一刻，刷新的時機沒抓準就會完全錯過，之後也補不回來（角色造型仍然會
  正確換成孵化後的樣子，只是沒有演那段動畫）。

**修法規劃（還沒執行）**：
1. 把 `maybeHatch` 的判斷也搬進 `feedPet()`（餵食是唯一會發 xp、因此唯一可能在單一次
   呼叫裡跨過孵化等級的動作）：扣庫存、加經驗值之後，比照 `settlePetRewards` 的寫法
   檢查這次更新後的等級是否剛好跨過 `PET_HATCH_LEVEL`、`claimedKeys` 還沒有
   `"hatched"`，是的話呼叫换裝邏輯並把 `justHatched` 一併傳進這次回應的 `toDTO`。
2. 前端 `pet-view.tsx` 的 `act()` 目前只在 `action === "feed"` 時 `setMood("eating")`；
   要加一段「這次回應帶 `justHatched: true` 的話改播 `setMood("hatching")`，不要播
   `eating`」——孵化是比吃東西更值得播的一次性里程碑，兩個動畫撞在一起時孵化優先，
   直接跳過那一口的吃東西動畫。
3. 順便檢查：目前只有 `feedPet` 會加 xp，之後如果有別的途徑也能加 xp（例如之後新增
   「分享」「每日任務」之類的獎勵），要記得同一套孵化檢查也要搬過去，不要只補
   `feedPet` 這一處，不然又會出現同一種「等級到了動畫沒跟上」的狀況。
4. 影響範圍：只改 `feedPet`（新增一段邏輯）跟 `pet-view.tsx` 的 `act()`
   （多一個分支判斷），不動 `settlePetRewards`／`maybeHatch` 本身，兩邊共用同一套
   孵化判斷邏輯，建議把 `maybeHatch` 的核心判斷抽成一個不吃 `PetDoc` 以外東西的小
   function，兩邊呼叫同一份，避免以後改孵化規則要改兩個地方。

**還沒決定的**：要不要現在就做這個修正。

- 位置與大小都寫成「佔角色幾成」的比例（`FOOD_SCALE / FOOD_LEFT / FOOD_TOP`），場地上
  的 180px 角色跟背包預覽的 130px 角色共用同一組數字，不用各調一次。
- `FoodBite` 自己管自己的格數（單列 7 格、演兩輪），**演完定格在最後一格（空盤）**
  不繞回第一格——繞回去的話蛋糕會在吃完之後整塊長回來再吃一次，看起來像沒吃到。
- 蛋階段也會出現了：之前擋掉是因為以為那張圖畫的是孵化後的角色，現在確認畫的是食物
  本身，蛋旁邊擺一塊蛋糕完全合理。
- `petEatingDurationMs` 改成取「角色動畫」與「食物動畫」兩者較長的那一個：蛋有自己的
  吃東西圖（2,940ms）就以它為準、食物演完先定格在空盤；孵化後角色只是待機，就以食物
  的 1,960ms 為準。

**餵食列終於可以用滑鼠拖了**（`useDragScroll`）。之前那次改 `aria-disabled` 只解決了
「手機觸到 disabled 按鈕整列不動」，桌機的狀況是另一個：那一列的捲軸是藏起來的
（`no-scrollbar`），而瀏覽器原生**不支援**按住往旁邊拖動捲動容器，所以桌機只剩「滑鼠
滾輪轉」一條路——沒人會想到要把游標移到那一列上面滾滾輪，看起來就是「滑不動」。

現在三種操作都通：手指滑（原生）、滾輪轉（既有的 `onWheel`）、**滑鼠拖**（新加的）。
兩個實作上的坑：
- **`setPointerCapture` 不能在 pointerdown 就抓**：抓了之後那一次 click 會改派給捕獲的
  元素（整列），底下的食物按鈕永遠收不到點擊、東西餵不下去（實測踩到）。改成「位移
  超過 4px、確定在拖」才抓，單純點擊全程不碰捕獲。
- 拖完要在捕獲階段吃掉那一次 click，不然放開手的位置剛好在某顆食物上就會順手餵下去
  一份。
- 事件全部在 `useEffect` 裡掛到元素上，不回傳一包 `onPointerXxx` 給 JSX 展開——那樣
  每次 render 都要碰一次 ref，新的 `react-hooks/refs` 規則會擋。
- 另外補上 `touch-action: pan-x`，明確告訴瀏覽器這一列只吃橫向手勢，直向交還給外層。

### 2026-11-16（續三）：十二種食物都有專屬動畫、放慢速度、滑動補間

**十二種食物的吃東西動畫全部到齊**。美術出圖時的檔名是另一套
（`candied_hawthorn_eat_7x1_3500x500.png` 這種），進專案時統一改名成
`intj-eating-<品項後半>.png`（跟最早那張 `intj-eating-cake.png` 同一個規則），
兩套名字不要同時存在。對照表就是 `FOOD_EATING_SPRITES`，id 後半對應檔名後半：
cookies／candiedhawthorn／icecream／salad／noodle／cake／skewer／frieddrumstick／
sushi／shrimp／crab／yuzu。

**動畫放慢**：食物動畫獨立一個 `FOOD_FRAME_MS = 240`（角色那套維持 140ms）。原本兩邊
共用 140ms，一份食物 14 格咬完只要 1.96 秒，一眨眼就沒了；放慢之後一輪 3.36 秒，
「咬一口、停一下、再咬一口」的節奏才看得出來。`petEatingDurationMs` 跟著改成取
「角色動畫」與「食物動畫」兩者較長的那一個（現在通常是食物那段）。

**餵食列的滑動補間——這次才真的找到原因**。先前試過在那一列加 CSS 的
`snap-x snap-mandatory scroll-smooth`，結果反而更糟。實際量過才確定：**CSS
`scroll-snap-type: mandatory` 會在每一次 `scrollLeft` 改變之後立刻把位置拉回最近的
吸附點，不分那次改動是放開手之後的收尾、還是使用者手指還按著正在拖**——實測拖到
一半（scrollLeft 應該是 40）時量到的已經是吸附點 89，整條列等於用跳的，正是
「看起來像直接切換一格」的來源。

所以 CSS 的 scroll-snap 全部拿掉（連每顆按鈕的 `snap-start` 一起），吸附改成自己在
JS 裡做（`useDragScroll` 的 `settle()`）：
- 拖曳途中只單純寫 `scrollLeft`，1:1 跟著游標，不會被任何東西拉走。
- 放開手（或滾輪、觸控原生捲動停下來後 debounce 120ms）才算出最近一格的左邊界，
  用 `scrollTo({ behavior: "smooth" })` 滑過去——實測拖到 40 放手後的連續取樣是
  `40 → 38 → 34 → 0`，是真的逐格補間滑過去，不是瞬間跳。
- 一格的寬度用前兩顆按鈕的 `offsetLeft` 差算出來（含 gap），版面改了不用跟著改。

### 待確認 2：股票／黃金的實際市值

**現況**：帳戶餘額是 `期初 + 收入 − 支出 ± 轉帳` 算出來的，所以「股票」帳戶現在顯示的是
**投進去多少錢**，不是**現在值多少**。要算市值，缺的不只是價格，是**持倉**（哪一檔、
幾股、成本）。

資料來源（都免費、免金鑰）：上市股票走 TWSE OpenAPI 的 `exchangeReport/STOCK_DAY_ALL`
（一支 API 拿到當日全部收盤價）、上櫃走 TPEx OpenAPI、黃金走台灣銀行黃金存摺牌價。
盤後資料一天只變一次，所以做成 **MongoDB 快取 ＋ 當日第一次請求才更新**
（`expenses.marketPrices`，以 `(symbol, date)` 當鍵），比照搭乘車 `transit.tdxCache` 的
做法，不用排程器也不會頻繁呼叫。

三種資料模型，**建議第 2 種、而且分兩步走**：

1. 手動市值（最輕，不接 API）：帳戶多一個「目前市值」欄位，自己更新。
2. **持倉 ＋ 自動報價**：股票／黃金類型的帳戶底下可以新增持倉（代號、股數、平均成本），
   市值 ＝ Σ(股數 × 當日收盤價)。先做「持倉 ＋ 手動報價」把資料模型與介面定下來，
   再接 API 把報價自動化（那時只是把一個欄位從手填換成每日更新，介面不用再改）。
3. 完整投資模組（配息、拆股、成本法、報酬率）——這是另一個工具的規模，不建議塞進記帳本。

**還沒決定的**：(a) 走第 2 種嗎 (b) 只做台股＋黃金，還是也要美股（美股免費來源較不穩）
(c) 黃金記「公克」還是「台錢」。

# 十三、養成圖片的載入成本分析（2026-11-18，先不執行）

> 要回答的是：**不重新出圖、不動現有檔案**的前提下，能把載入壓到多快。

## 13.1 現況的數字

`public/expenses` 合計 **50.5 MB**（169 個檔案）。最重的幾類：

| 類別 | 張數 | 單張 | 小計 | 實際尺寸 |
| --- | --- | --- | --- | --- |
| 角色待機精靈圖 `intj-model-*-idle.png` | 6 | ~3.0–3.3 MB | **~18.7 MB** | 3500×1500（7 欄 × 3 列，單格 500×500） |
| 吃東西動畫 `intj-eating-*.png` | 12 | ~1.3 MB | **~15 MB** | 3500×500 |
| 蛋（待機／孵化／吃） | 3 | 1.6–3.0 MB | ~6.3 MB | 3500×1500 |
| 首頁主視覺 `main-kv-*.png` | 4 | ~1.3–1.4 MB | ~5.5 MB | 1239×984 |
| 養成背景 `pet-bg-*.png` | 6 | ~450 KB | ~2.6 MB | 900×1600 |

**一進養成頁實際會下載**：背景 1 張（~450 KB）＋目前造型 1 張（**~3.2 MB**）＋彈窗九宮格切片
＋食物圖示。也就是說，首屏的瓶頸幾乎都在那一張角色圖。

**真正的大戶是商店／背包的「服裝」分頁**：縮圖（`petItemThumb`）是用 CSS `background` 把
精靈圖的第一格裁出來，所以一格 60px 的縮圖**背後是整張 3.2 MB 的原圖**。開那個分頁等於
一次再抓最多 ~19 MB。

## 13.2 不動圖片檔案能做的事（依投報率排序）

1. **給靜態圖加長效快取頭**（最省力、效果最直接）
   `next.config.ts` 的 `headers()` 把 `/expenses/*.png` 設成
   `public, max-age=31536000, immutable`。這些檔名一旦發布就不會變，第二次之後完全不用
   再下載、也不用發 304 的往返。**代價**：之後要換圖必須換檔名，不能原地覆蓋。
2. **縮圖改走 `next/image`**
   Next 的圖片最佳化是「請求時轉檔」，**不會動到原始檔**：指定 `width` 之後，瀏覽器
   實際拿到的是幾十 KB 的 WebP／AVIF。商店／背包那 6 張服裝縮圖最划算（19 MB → 數百 KB）。
   注意：**動畫本身不能這樣做**——它靠 `background-position` 一格一格換，必須是原圖。
3. **先載眼前要用的，其他延後**
   角色圖與背景加 `<link rel="preload" as="image">`；商店／背包的縮圖加 `loading="lazy"`，
   並且只在那個分頁真的被打開時才 render（現在是彈窗一開就把每個分頁的格子都畫出來）。
4. **吃東西動畫在閒置時預抓**
   目前是點下去才換 `src`，所以第一次餵某種食物會卡一下。可以在 `requestIdleCallback`
   裡預抓「背包裡數量最多的那一種」，不影響首屏。
5. **Service Worker／Cache API 背景預快取**
   第一次進站之後，在背景把六套造型抓進快取，之後換裝是瞬間的。成本是多一個 SW 要維護。
6. **減少解碼成本**
   3500×1500 的 PNG 解碼大約要 21 MB 記憶體，低階手機會卡住主執行緒。`decoding="async"`
   ＋ 對離屏格子用 `content-visibility: auto`，可以讓解碼不要擋住互動。

## 13.3 如果哪天願意動檔案

轉成 WebP／AVIF 大約省 **70–85%**（18.7 MB 的角色圖 → 3–5 MB），而且 sprite sheet 的
格式、尺寸、切法都不用改，是投報率最高的一步。再進一步才是「把 7×3 的大圖拆成單格」
或「待機只留必要的幾格」。
