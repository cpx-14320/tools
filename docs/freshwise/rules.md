# 菜鳥買菜記（freshwise）— 規則與執行規範

> 動這個工具之前先讀這份。這裡只寫**現在成立的結論 ＋ 一行為什麼**；
> 「原本是 X、後來改成 Y」的來龍去脈在 [history.md](history.md)，待辦在 [status.md](status.md)。
> **色票、字級、間距在 [design.md](design.md)**——改樣式讀那份，這份不重複。
> 跨工具共通的規則（設計系統不互 import、金鑰只能在 server、資料存帳號）在 [../README.md](../README.md)。

## 0. 這個工具要解決什麼

給**不懂買菜價格的人**一句能用的話：「今天這樣菜，你去市場付多少算合理」。

所以每個決定都回到這個人身上：他要去的是菜市場不是批發市場；他看不懂上價中價下價，但看得懂
「比平常便宜 12%」；他寧願看到「大概 40～60 元」也不要一個精確但錯的數字。

## 1. 數字的規則（定案，不要再改）

| # | 規則 | 為什麼 |
| --- | --- | --- |
| R1 | **資料層一律存元/公斤**，欄位都叫 `*Kg`；換算只在 `price-text.tsx` 發生（1 台斤 = 0.6 公斤） | 兩種單位混在同一欄位，遲早有人拿 1.8 倍的數字去跟 1 倍的比，而且錯得很安靜 |
| R2 | **漲紅跌綠**，±1.5% 以內當持平 | 台灣看盤習慣，對買菜的人綠色剛好是好消息。不設死區的話畫面全是「漲 0.4%」，真正的暴漲被淹沒 |
| R3 | **划算度比的是「它自己平常的價格」**，±10% 以外才標划算／偏貴 | 高麗菜 20 元跟草莓 300 元沒得比。不到 30 天不下判斷；不到 300 天時基準寫「過去 N 天的平均」而不是「近一年」 |
| R5 | **休市日退回上一個交易日，而且要在畫面上說** | 批發市場週一整天沒有資料，不說就會被當成今天的價 |
| R6 | **「今天」用 `Asia/Taipei`**（`dates.ts` 的 `todayISO()`） | 正式環境在 Vercel（UTC），用 UTC 的話台灣凌晨 0～8 點整個工具顯示昨天，**每天都會發生** |
| R7 | **日期一律用 `YYYY-MM-DD` 字串流通**，不在模組間傳 `Date` | 頁面是 Server Component，`Date` 跨邊界序列化再解析，時區一不小心就差一天 |
| R8 | **代表價：有成交量取交易量加權平均、沒有的取中位數** | 加權平均才是「今天成交的菜平均多少錢」；訪價一筆填錯就會把算術平均拉走（香蕉標 100 那天平均 44、中位數 34） |
| R9 | **沒有實測價就給區間，不給假的精確數字** | 實測回推「零售÷批發」是 1.2～4.5 倍（香蕉 1.2、蘿蔔 4.5），用單一係數會錯到讓人買錯 |

R9 的細則：倍數**從當天的資料即時算**（`prices.server.ts` 的 `estimateRatios`，每類至少三個
樣本，算不出來才退回 `catalog.ts` 的 `ESTIMATE_RANGE`）；用**四分位距 P25～P75** 不是
min～max（青椒的 min～max 是 34～141，四倍寬的區間等於在說「我們不知道」）；**推估的品項
不顯示漲跌與划算度，也不參加那兩種排序**。

## 2. 誠實標示（R4）

1. **沒有實際訪價的數字一律標「估算」。** 超市量販整個場所都是推估的（沒有任何免費開放資料）；
   傳統市場是「臺中有訪價的品項用真實訪價、其他品項用批發價推估」。
2. **超市量販不掛任何真實品牌。** 把推估的數字掛在品牌下面，等於宣稱「這家店今天賣這個價」。
3. **批發價不是消費者付的錢。** 它可以出現在比價表與走勢圖（看漲跌最準），但「最便宜」這種
   推薦只在消費者真的買得到的場所之間比。批發市場因此**不是可選場所**（`selectable: false`）。
4. **首頁頭條優先用實際訪價的品項**，只有推估值時句子裡標「（推估）」——推估值經係數放大後
   波動更劇烈，很容易霸占「今天最划算」。
5. 每一頁底部寫出資料來源（`theme.ts` 的 `copy.sourceNote`）。

## 3. 場所與品項目錄

三個場所用**使用者會去的地點**命名：`market` 傳統市場、`super` 超市／大賣場（兩者合一，因為
兩邊都沒有公開架上價，給不同數字等於憑空編出精確度）、`wholesale` 批發市場（不可選，理由見上）。

### 品項名稱：主名用俗名，行情正式名放 `aliases`

```
{ code: "FC7", name: "小黃瓜", aliases: ["花胡瓜", "刺瓜"], … }
```

農業部用的是作物正式名（甘藍、蕹菜、花胡瓜、蓬萊米）。目錄原本照抄，結果食譜寫「小黃瓜」、
點進詳情頁卻看到「花胡瓜」。現在主名稱是俗名，正式名降為別名——`matchesKeyword` 比對
`name` ＋ `aliases`，所以兩種名稱都搜得到、詳情頁也會列出「又叫 花胡瓜、刺瓜」。

**這跟取價無關**：價格是用 `source-map.ts` 的 `match` 關鍵字比對開放資料的作物名稱，那邊
仍然要寫**正式名稱**。不要「順手統一」把 SOURCE_MAP 也改成俗名，那會讓整類菜查不到價。

### 三份清單分得開

| 清單 | 內容 | 畫面用哪一份 |
| --- | --- | --- |
| `CATALOG` | 全部品項（含目前沒有資料來源的） | 不要直接用 |
| `TRACKED_CATALOG` | 有 `SOURCE_MAP` 對應、真的查得到價的 | **行情頁、品項選擇器一律用這份** |
| `PANTRY` | 食譜會用到但**行情查不到**的（加工品、未收錄生鮮） | 只用在「搜不到」時的解釋 |

`PANTRY` 刻意不併進 `CATALOG`：併進去會跑進行情清單（一排永遠查無價格）、品項選擇器（勾進
菜籃後因為菜籃只畫有行情的項目會憑空消失）、詳情頁（空走勢圖）。它們不是「暫時沒資料的品項」，
是**沒有價格這個欄位的東西**。`pantryMatches` 用**開頭比對**不是 `includes`——搜「菜」用
includes 會命中「紫菜」，於是一個有五十筆結果的搜尋上面冒出一句「紫菜沒有行情」。

## 4. 資料來源

| 類別 | 批發 | 傳統市場零售 |
| --- | --- | --- |
| 蔬菜、水果 | 農業部農產品交易行情（全國 22 市場） | **只有臺中市公有零售市場有訪價** |
| 漁產 | 農業部漁產品交易行情（18 市場） | 臺中 7 種 |
| 肉類 | ❌ 完全沒有（毛豬拍賣價是整頭豬的均價，不能當豬肉零售價） | 臺中有豬牛雞鴨 |
| 蛋品 | 只有雞蛋的「產地價」 | 臺中有雞蛋、鴨蛋 |
| 米 | 糧價 API | **唯一全國各縣市都有每日零售價的來源** |

所以「這個數字是實際訪價還是推估」不是看場所就能決定的，要看那個品項在那個場所有沒有來源
（`prices.server.ts` 的 `deriveQuote`）。API 的參數坑（`StartDate` 必填、民國年有兩種格式）
記在 `moa-client.ts` 的檔頭。

價格不在頁面上算：伺服器端（`prices.server.ts`）整理好整本 `PriceBook` 當 props 傳下去。
`search.ts` 把「品項 ＋ 今日行情 ＋ 漲跌 ＋ 划算度 ＋ 當季」綁成一個 `PriceRow`，不要讓清單
元件各自再算一次——這幾件事在四個頁面都會一起出現。

## 5. 畫面規則

- **430px 寬的手機框**（`.fw-phone` 的 `max-width`）。所有尺寸決策從這個寬度出發。
- **整個工具只有一種紅綠徽章：漲跌**（跟前一個交易日比）。**划算度沒有徽章、也沒有結論句**
  ——兩個百分比擺在一起、基準一個是昨天一個是近一年，會被讀成同一件事，甚至互相矛盾
  （跌 30% 卻說「比平常貴」）。清單列底下那行 meta 只講「這個數字能不能信」：推估範圍、
  歷史累積中、當季；都不適用就不畫那行。詳情頁用**區間指示條**（最低 ── ● ── 最高）表達
  同一件事的事實版本，讓使用者自己看位置，不替他下結論。
- **共用元件不要再刻第二套**：`PriceListRow`（清單列）、`Paper`（紙卡，`variant` 控制樣式）、
  `BottomSheetModal` / `EditorSheet`（彈窗）、`SegmentedTabs`、`Badge`、`GoTopButton`。
  同一種樣式在兩個以上的地方出現過，就該收進 `components/freshwise/ui.tsx`。
- **class 用 `cx()` 串**（`theme.ts`），不要用模板字串——條件沒中會留下 `class="fw-badge  "`
  這種空格尾巴。
- **徽章的語意色在 `badges.tsx`**，不要在頁面裡寫 `className="fw-xxx"` 配一條只有它在用的
  CSS。「什麼情況該亮什麼顏色」是徽章的事，散出去下一個人改配色就改不到。
- 骨架（skeleton）在這個工具已經全部移除，只有搭乘車還在用。

## 6. 素材

**母圖與網頁用圖是兩件事，放兩個地方：**

| | 位置 | 規則 |
| --- | --- | --- |
| 母圖 | `小工具素材/圖片未壓縮/freshwise/`（595 張） | 不因網頁需求縮放、轉格式、改名。檔名照網頁檔名命名 |
| 網頁用圖 | `public/freshwise/`（595 張，全部 WebP） | 可以縮放、壓縮、改副檔名；壞了重跑腳本 |

```
npx tsx scripts/freshwise-build-web-images.mts          # 從母圖重建全部
npx tsx scripts/freshwise-build-web-images.mts --dry    # 只看計畫，幾秒跑完
npx tsx scripts/freshwise-build-web-images.mts pet-     # 只重建一組
```

尺寸依據是「**畫面最大顯示尺寸 × 3**」——沒有素材需要超過 430×3＝1290px。每組的目標與理由
寫在腳本的 `RULES` 裡（夥伴 640、品項與料理 256、介面圖示 192、花園背景 1290…）。
兩個不重新編碼：`home-quest-paper`（`border-image` 的切片數值綁原始像素）、
`page-hanging-title-*`（已是輕量 WebP）。

母圖在素材庫有多個版本時：**先排除「待人工確認」那類資料夾，再取解析度最大的**。踩過的坑是
矮木檯挑到未裁切的 2172×724（網頁要的是裁切版），而 CSS 是 `background-size:100% 100%`，
比例不一樣就會被擠變形。

**檔名規則**：

```
item-<品項代碼>.webp            品項（code 對 catalog.ts）
item-farm-<農業部作物代號>.webp  照來源代號出圖的那幾批（對照在 art-assets.ts）
dish-<料理>.webp                100 道料理（對照在 group-icons.ts）
ui-<功能>.webp                  介面圖示（名稱在 game-art.tsx 的 GAME_ICONS）
pet-<食材>-<角色>-stage-0N[-<表情>|-action-<動作>].webp
```

改副檔名會牽動七處路徑組裝，最容易漏的是 `item-icon.tsx` 的 `ITEM_CODE`／`CATEGORY_KEY`
——它們**從路徑反推品項代碼**，漏改不會報錯，只會讓整排品項圖變留白。所以
`check:freshwise` 有一段「素材路徑真的存在」直接對磁碟驗。

## 7. 食譜

- 食譜是**這個工具提供的內容**，寫死在 `recipes.ts` / `recipes-extra.ts`，不存進使用者資料。
  使用者只擁有一個數字：「我要煮幾人份」（`BasketGroup.servings`）。
- `main` / `extra` 的分界**不是「是不是調味料」**，而是由寫食譜的人標：蒜頭在蒜泥白肉是主角、
  在番茄炒蛋是配角，規則自動分會分錯。`main` 按人份換算且有 `code` 的算進成本；`extra` 的
  具體份量換算、「適量／少許」保留文字、一律不算錢。
- 份量存三個欄位：`display`（給人看的「半顆（約 100 公克）」）、`grams`、`qtyCatty`（計價用）。
  只存 `qtyCatty` 會在畫面上出現「0.17 台斤洋蔥」這種沒人這樣講的話。
- 沒有代碼的 `main` 食材（板豆腐、油麵…）金額欄寫**「無行情」**不是「—」（「—」看起來像資料
  還沒載好），而且**不掛「不在菜籃」徽章**——它永遠進不了菜籃。
- 食譜與菜籃**刻意不互相覆蓋**。套用拆成兩顆按鈕：「把缺的 N 樣加進菜籃」（只新增，低風險）
  與「N 樣份量改用食譜的量」（**會覆蓋**使用者填的常買份量，所以文案一定要留「改用」兩個字）。

## 8. 養成（夥伴）

- 進度**存在帳號底下**（`/api/freshwise/companion`），不是 localStorage。畫面先用
  `companions.ts` 的純函式樂觀更新，再把「發生了什麼事」送上去，伺服器跑同一組函式，回應到了
  以伺服器為準。
- **數字只定義一次**：`WATER_DEW_COST`（澆水 10 露珠）、`WATER_XP_GAIN`（+10 成長）、
  `PLAY_XP_GAIN`（+2）、`QUESTS[].reward`（每項 20）、`QUEST_STAMP_REWARD`、`XP_PER_LEVEL`。
  **畫面上的提示不要自己寫數字**——澆水的提示是拿「實際增加了多少」組句子，改了常數訊息
  會自己跟著變。以前澆水成本在按鈕文案、disabled 判斷、扣款三處各寫
  一個 `3`，改數字漏掉按鈕就變成「按得下去但沒反應」。
- **階段門檻只在 `companions.ts` 的 `unlockedStage`**（1–3 嫩芽、4–7 成長、8+ 成熟），
  `petStage` 轉呼叫它。
- **畫哪一張圖只看階段，不看等級**：`petBaseFile(id, stage)`、`PetArtwork stage={…}`。
  「現在要畫第幾階」的唯一出口是 `petLookStage(state, id)`，它把等級與使用者在圖鑑挑的外觀
  （`state.look`，`0`＝跟等級走）解決掉。
- 外觀**只能挑已經長到過的階段**——提前換成第三階，升級那一刻就沒有變化了。圖鑑三階都畫，
  還沒拿到的套「沒取得」的樣子，而且跟「還沒結識的夥伴」用同一組數字（`opacity:.6;
  filter:saturate(.35)`）——「沒取得」在這個工具裡只有一種長相。
- **新帳號的露珠是 0**，澆水要先完成任務換。一開始就送一壺水會讓第一次澆水變成沒來由的事。
- **把關只有一個地方：store 的 `care()`。** 它讀的是 `current.current`（ref，`apply()` 裡
  同步更新），不是 React state——連點時 state 可能還是舊的，拿它判斷就會放行第二下。
  `care()` 回傳「有沒有真的發生」，畫面據此決定要不要播動畫；按鈕的 `disabled` 仍然用 state，
  但那是給眼睛看的、不是把關。扣款與成長在 `careForCompanion` 裡是同一個物件算出來的，
  所以不可能「扣了卻沒加」。
- **提示文字裡的數字一律用「實際差額」**（`next.dew - 目前的 dew`），不要讀常數或寫死，
  而且**要在 `apply()` 之前算**——`apply` 會換掉 `current.current`，之後相減都是 0。
  澆水、陪玩、領獎三處都是這個寫法。
- 表情與照護動作的圖是 `unoptimized` 直接載入原檔，所以**必須維持輕量**；平常樣子走
  next/image 最佳化。

## 9. 怎麼驗

```
npx tsc --noEmit
npx eslint app components lib scripts
npm run check:freshwise                                  # 289 項，純函式，不用資料庫
npx tsx scripts/freshwise-companion-check.mts            # 26 組，養成與素材
npx tsx scripts/freshwise-missing-art.mts                # 缺圖清單（目前 0）
```

要資料庫（`.env.local`）的兩支：`freshwise-user-data-check.mts`（菜籃與偏好的讀寫）、
`freshwise-activity-code-check.mts`（活動序號）。`freshwise-sync.mts` 不是測試——它會真的去
農業部抓資料寫進 Mongo。

`check:freshwise` 測的是純函式與素材路徑，**不測 UI**。按鈕有沒有接對、版面好不好用，要真的
開瀏覽器走一遍。

## 10. 踩過的坑（留著避免再犯）

- **Mongo 把 `undefined` 存成 `null`**，所以讀回來的欄位不會是 undefined。只宣告
  `number | undefined` 的話，`x !== undefined` 在型別上過得去、執行時卻會拿 null 去呼叫
  `toLocaleString` 然後整頁 500。型別要寫 `number | null`。
- **`overflow-hidden` 會讓裡面的 `position: sticky` 失效**（瀏覽器改以那個容器當捲動參考）。
- **假價格必須可重現**：同一組輸入算出不同數字會讓 Server Component 的 hydration 直接報錯，
  而且只在正式環境明顯。
- **`?v=N` 查詢字串**是 CSS 背景圖的快取破壞用的，改圖不改檔名時要記得加。
