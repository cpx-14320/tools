搭車咻一下

整合公車、台鐵、捷運、高鐵與 YouBike 的個人化交通查詢平台——這份案例研究拆解每一種交通工具背後不同的資料流程、快取策略與互動設計。

5種交通工具整合
2層快取架構
9種公車客製化鍵盤
Dijkstra捷運最短路徑

專案總覽

「搭車咻一下」讓使用者在同一個平台查詢公車、台鐵、捷運、高鐵與 YouBike，不必在不同官方網站或 App 之間切換。 比起單純展示班次，這份案例研究更想說明的是：每一種交通工具的資料特性都不同——台鐵／高鐵用出發站＋抵達站取得實際班次， 公車用縣市＋路線＋方向＋站牌找即時到站，捷運靠站間行車時間與轉乘關係計算路徑，YouBike 則是站點搜尋與距離排序。 平台另外整合「我的行程」、天氣、備忘錄與首頁內容管理，讓交通查詢配合日常使用習慣，而不只是一次性的單次搜尋。

S1
基礎線・架構

技術棧與共用外框

前端使用 Next.js、React、TypeScript 搭配 Tailwind CSS 建置；Next.js App Router 負責路由與 API Route，React 管理頁面狀態與非同步資料，TypeScript 為每種交通工具的站點、班次與到站狀態定義資料型別。站點選擇、日期／時間選擇、行程編輯等功能都拆成共用元件，避免不同頁面重複撰寫相似邏輯。

登入與工具權限

交通工具頁面外層的共用 Layout 會先檢查登入狀態與工具權限；未登入導向登入頁，沒有權限則顯示提示畫面。個人資料 API（行程、備忘錄、橫幅等）另外用 requireTool("transit") 再驗證一次，確保依使用者識別碼讀寫資料。

TransitShell 共用外框

負責整合桌機與手機的導覽與頁面結構，header／footer 與互動樣式統一管理，讓每個頁面只需要處理自己的功能，不必重複刻一份外框。

S2
個人化線・首頁

首頁：查詢入口與每日使用記憶

首頁把交通工具選擇、站點設定、日期時間、天氣與備忘錄整合在同一畫面。切換公車／台鐵／捷運／高鐵時，介面會換上對應的欄位——台鐵與高鐵用出發／抵達站，捷運用起訖捷運站，公車則是縣市＋路線＋方向＋站牌的「路線優先」模式。最後使用的交通工具會存進 localStorage，重新整理頁面也能恢復上次模式。

天氣卡片

可自訂多個縣市＋行政區，各自顯示今天／明天兩張卡片，載入期間用 Skeleton Loading 避免畫面跳動。

小小備忘錄

文字、圖示與提醒時間存在 MongoDB，新增修改後前端即時更新清單筆數，供下次 Skeleton 列數預估。

主視覺與週末小旅行

首頁主視覺與週末小旅行橫幅由個人化內容提供，使用者沒自訂時退回預設內容，避免首頁空白。

S3
公車線・互動設計最濃的一站

公車查詢：客製化鍵盤與即時到站

公車沒有固定的「起訖站」概念，操作核心是「縣市＋路線／站牌＋方向」。使用者可能只記得路線編號或某個站名，介面因此設計成可以先搜路線再選方向站牌，也可以反過來先搜站牌再看有哪些車經過。

依縣市客製化的快捷鍵盤

不同縣市的路線命名習慣不同，keypadForCity() 把數字鍵、該縣市專屬的快捷字元與刪除鍵組成動態鍵盤——例如台北市搜尋「紅29」只要按紅色鍵再按 2、9，不必切換輸入法逐字輸入。

避免一開彈窗就觸發搜尋

路線／站牌搜尋都打真實 TDX 資料，不是前端固定清單。查詢字串為空時完全不送出請求，前端用 200 毫秒 debounce，已查過的條件還會用前端快取，避免每按一個字就重打一次 API。

特殊命名路線

像「東山咖啡線」這種純文字命名、沒有數字的路線，鍵盤打不出來，所以另外提供「瀏覽文字命名路線」入口，只有使用者主動點開才會查詢。

附近站牌：跨縣市彙整＋依站名去重

點選定位後才要求 GPS 權限，取得座標後用 Promise.all() 並行查詢所有支援縣市的站牌位置，依距離排序取最近 20 筆——跨縣市查詢是為了不漏掉行政區交界另一側更近的站牌；合併時依站名去重，保留距離最近的那一筆，避免重複登記的站牌占掉顯示名額。

S4
鐵道線・台鐵與高鐵

台鐵與高鐵：時刻表、票價與容錯

台鐵結果頁用 Promise.allSettled() 並行取得每日時刻表、出發站即時誤點與起訖站票價三種資料。時刻表是必要資料，取不到就回傳錯誤；誤點或票價取不到時，班次仍會顯示，只是少了對應資訊——不會因為一項失敗就整頁空白。

票價怎麼選

從 ODFare 資料挑最短行駛距離的那組，再以 TicketType = 1 搭配 FareClass = 1 取全票價，避免不同距離或非一般全票的價格被誤用。

班次是否已過期

用台灣當地「現在」時間判斷，不是用使用者搜尋時選的時間——重新載入舊查詢條件時，尚未發車的班次不會被誤判成過期。

高鐵站碼對照

THSR_STATION_ID 把顯示站名轉成 TDX 站碼，會先處理「站」字尾等格式差異再查表。

早鳥票價

只有在 API 確實提供早鳥票價欄位時才顯示折扣，沒有這個欄位就不顯示，不會自己假設一個折扣值。

S5
捷運線・Dijkstra 最短路徑

捷運路線計算與轉乘

捷運是案例研究中唯一用到圖論演算法的部分。系統把站點與站間行車時間建成路網圖，有明確轉乘關係的車站依 METRO_TRANSFER_HUBS 另外加一條轉乘邊（成本估算 180 秒），轉乘關係由程式明確定義，不是單靠站名相同就推斷能轉乘。接著用 Dijkstra 演算法找出起訖站之間時間最短的路徑，取得總車程、停靠站數、轉乘站與後續線別，依官方線色（G、R、O 等）標示。

!

跨系統查詢的真實狀態：後端已有 computeCrossSystemMetroTrip() 可整合台北／新北／機場捷運與部分輕軌的路網，但目前前端 results-view.tsx 的跨系統查詢仍走另一條分支（轉乘站名稱對照＋預設估算值），對外的 API Route 也只呼叫單一系統版本——「後端已有的函式」跟「前端是否完整接上」是兩件需要分開看待的事。

!

結果時間列的性質：目前前端版本是依規則在 06:00–24:00 間，以平均每 8 分鐘一筆的方式生成約 135 筆時間列，這是介面展示用的生成資料，不是向 TDX 取得的 135 班官方實際發車紀錄。

S6
個人化線・我的行程

我的行程：可重複使用的查詢條件

「我的行程」保存的不是某一班車的靜態收藏，而是一組可以重複查詢的條件——例如一條下班通勤路線設定 16:00–16:26，之後按「搜尋班次」就會重新查詢並只保留這個時間範圍內的結果。使用者可以建立自己的分類（上班／下班／假日出遊），分類存在 transit.tripGroups，常用行程存在 transit.frequentTrips 並用 groupId 關聯。

整批同步，不逐筆打 API

常用行程清單透過 PUT /api/transit/frequent-trips 一次送出完整清單，後端依識別碼比對、更新、新增並刪除不在清單中的項目，回傳最新清單後前端直接更新畫面。

一站式新增行程

在查詢結果卡片按「加入行程」時可以直接建立新分類並加入，不必先離開結果頁建立分類再回頭操作。

S7
微旅行線・YouBike 與天氣

YouBike 站點搜尋與天氣預報

YouBike 功能查詢站點名稱與座標（getUbikeStations()），附近站點一樣先定位再並行查詢所有支援縣市，依距離排序顯示最近 20 筆，並附外部地圖步行導航連結。天氣則支援自訂多個縣市＋行政區，dayOffset 控制取今天或明天的預報，日期計算用 UTC+8 推算台灣當地日期，避免伺服器時區誤判。

!

誠實標註範圍：目前程式只查站點名稱與座標，沒有呼叫即時可借車／可還車位數的 Availability 端點，所以這一頁應該稱作「YouBike 站點搜尋」，不是即時車輛數查詢。

S8
基礎線・雙層快取

TDX 外部 API 的雙層快取

交通資料的即時性不同，快取也分開處理：tdxGet() 先查伺服器記憶體 Map（同時也存進行中的 Promise，併發呼叫可以共用同一次請求）；沒有有效資料才查 MongoDB 的 transit.tdxCache，這一層能撐過 Serverless 執行個體被回收的情況。Token 也在記憶體快取，到期前預留 60 秒避免用到快過期的 Token。

資料類型預設快取期限原因
一般 TDX 查詢60 秒降低短時間重複請求
台鐵車站清單24 小時車站資料變動頻率低
公車路線與站序24 小時路線與站序較穩定
捷運站間時間／線別／票價24 小時靜態交通資訊不需每次重抓
YouBike 站點名稱與座標24 小時站點位置相對穩定
中央氣象署預報30 分鐘需要定期更新預報

公車另外在 BusRoutePickerModal 疊了一層模組層級的前端快取——路線／站牌搜尋快取 5 分鐘，含即時到站的站序／站牌詳情快取 30 秒，彈窗關閉再打開仍能重用資料。前端快取降低重複操作造成的內部請求，後端快取降低對 TDX 的重複請求，兩層用途不同、互相補足。

S9
基礎線・資料結構與 API

MongoDB 資料結構與 API 總覽

個人化資料（行程分類、常用行程、備忘錄、首頁橫幅、週末小旅行）多數採同一種「整批同步」模式：前端送出目前完整清單，後端依識別碼比對差異後更新、新增、刪除，回傳最新清單。這能減少每個表單欄位各自打一次 API 的需求，但也只是差異同步，不等同於跨多個 Collection 的交易式原子更新。

終點
總站・專案特色

技術特色總結

「搭車咻一下」的重點不只是整合多種交通工具，而是針對每一種交通資料採取不同的處理、快取與互動方式：

1

多交通工具整合——台鐵、高鐵、捷運、公車、YouBike 共用平台入口，各自保留查詢規則。

2

捷運路徑演算法——站間行車時間與轉乘關係建圖，Dijkstra 計算同系統最短時間路徑。

3

公車客製化輸入——依縣市提供對應命名習慣的鍵盤，支援文字路線、站牌詳情與附近站牌。

4

雙層快取策略——記憶體＋MongoDB，依資料變動頻率設定不同 TTL，前端另疊 debounce 與模組快取。

5

個人化常用行程與首頁——分類、路線、時間區間、天氣、備忘錄、主視覺整合成每日會用到的查詢捷徑。

6

前後端分工清楚——前端處理互動顯示，後端負責參數驗證、外部資料整合、轉換、快取與個人資料保存。

🗒️ 仍在核對的事項

這份案例研究也誠實標註了目前程式快照還不能完全確認的部分——不假裝已完成，才是真的可信。

最快／最便宜／直達篩選：老師回饋提到這些操作，但目前 results-view.tsx 快照尚未找到完整實作，需要補上對應程式碼才能說明各交通工具的排序規則。
跨系統捷運：後端已有多系統路網計算函式，前端快照仍是預設估算分支，需要確認是否已在其他版本整合。
捷運時間列：目前結果頁用每 8 分鐘生成的時間列，不應視為官方實際班次；若有正式時刻表版本，之後需要更新本文件。
YouBike 即時車輛數：目前只查站點名稱與座標，並未確認即時可借車／可還車位數功能。
完整會員系統與部署設定：已確認工具層級的登入與權限檢查，但完整註冊、Session 管理與部署監控仍需對應原始碼確認。
